# ADR-0003：为何基于 Spug 二开而非自研

- 状态：已接受
- 日期：2026-09-16（补记；决策实际发生在 2026-08-25 选型调研）
- 关联：ADR-0001

## 背景

项目目标是把「平台工程 + 自动化运维」做成一套可复现、可验证的完整形态。开工前有两个方向：

1. **自研平台**：从零写 Web 平台 + Ansible 集成；
2. **基于开源平台二开**：选一个真实在用的开源运维平台，把精力放在增量能力上。

选型调研（2026-08-25）对比了 GitHub 上的主流开源运维平台，Spug 关键指标：
11,078 star、上游活跃（640 提交）、无 Agent 设计、Django + React 技术栈、AGPL-3.0。

## 决策

**基于 openspug/spug v4.0.1 二开**，项目名 OpsForge。理由：

1. **时间预算的去向**：主机纳管、在线终端、文件分发、应用发布这类平台基建，自研要
   花掉大部分工时，但重复造轮子学不到新东西。二开把工时全部投到 Ansible 引擎、
   巡检、自愈、网络自动化这些增量能力上。
2. **代码量适中可通读**：Spug 后端规模小（315 个跟踪文件），能在合理时间内读懂
   全链路——这是"敢在它上面改"的前提，也逼着人读真实生产代码而非教程代码。
3. **栈匹配**：Django + Channels + React 是主流组合，二开过程中学到的东西可直接迁移。
4. **无 Agent 架构**与实验环境契合：7 台容器节点只需要 sshd，6GB 内存预算跑得动。
5. **AGPL-3.0 允许二开**（保留许可与上游版权即可），个人项目无商用顾虑。

## 后果

- ✅ 二开增量全部是"自动化运维"本身（行数见 README「二开统计」），模块边界清晰、
  每块有实测数据。
- ✅ 有一套真实平台做对照：接口风格（`{data, error}` 信封）、鉴权、前端封装都按
  上游惯例走，避免"玩具项目"味。
- ✅ 全部能力可量化、可复现：每个模块都有实测记录（experiments/）与验收用例
  （tests/acceptance/）。
- ⚠️ **基线 lineage 复杂性**：上游 master（2.x 线）与 v4.0.1（独立分支）并存，工作区
  与运行容器不同源——以"容器内实际运行代码"为接口核对基准，见 ADR-0001。
- ⚠️ 上游锁定的依赖版本带存量漏洞（django/sqlparse 等），平台侧只能知情接受并记录；
  自建部分（新增依赖）要求 pip-audit 零已知洞。
- ⚠️ AGPL 要求公开仓库保持同许可、保留版权头——发布流程多一条检查项。
